# Agent Spec

## Overview

An SRE diagnostic agent that receives alert notifications from Cloud Monitoring alert policies via Pub/Sub, investigates the alert by querying Cloud Logging and Cloud Monitoring APIs, and publishes a structured diagnosis report (root cause, evidence, suggested next steps) to a Pub/Sub topic for downstream consumers.

The agent is multi-project and multi-service capable — it derives which project and service to investigate from the alert payload.

## Example Use Cases

1. **Cloud Run 5xx spike alert** — Alert policy fires on `run.googleapis.com/http5xx_ratio` exceeding threshold for `my-service` in `project-abc`. Agent queries Cloud Logging for error logs around the alert window, checks related metrics (latency, CPU, memory), correlates, and publishes a diagnosis: "Likely cause: OOM kills in revision `my-service-xyz` — memory usage hit limit at 14:32, followed by 503 responses. Suggested action: increase memory limit or investigate memory leak."

2. **GKE pod crashlooping alert** — Alert on `kubernetes.io/pods/crash_loop_backoff` for `checkout-service` in `project-xyz`. Agent pulls kube logs, checks resource metrics, and identifies the root cause (e.g., config map change broke the service).

3. **Elevated latency alert** — Alert on p99 latency for an API. Agent correlates with deploy events, error logs, and downstream dependency metrics to identify the culprit.

## Tools Required

| Tool | Purpose | API | Auth |
|------|---------|-----|------|
| `query_cloud_logging` | Fetch log entries filtered by project, service, severity, time range, and optional text filter | Cloud Logging `entries.list` | Service account / ADC |
| `query_cloud_monitoring` | Fetch time-series metric data for a given metric, project, service, and time range | Cloud Monitoring `projects.timeSeries.list` | Service account / ADC |
| `list_metric_labels` | Discover available labels/metrics for a given project (helps agent adapt to unknown services) | Cloud Monitoring `projects.metricDescriptors.list` | Service account / ADC |
| `publish_diagnosis` | Publish structured diagnosis JSON to an output Pub/Sub topic | Pub/Sub `projects.topics.publish` | Service account / ADC |

## Architecture

Single agent (no sub-agents). The agent receives an alert event, uses its tools to gather context, reasons about the findings, and publishes the diagnosis. The `ambient-expense-agent` recipe pattern (event-driven, no chat loop, workflow-based) is the architectural model.

## Data Flow

1. Alert policy publishes to Pub/Sub input topic → agent consumes the message
2. Agent parses alert payload (project, alert policy name, firing condition, affected resources, time window)
3. Agent calls `query_cloud_logging` and `query_cloud_monitoring` with derived filters
4. Agent reasons over collected evidence
5. Agent calls `publish_diagnosis` with structured report to output Pub/Sub topic

## Constraints & Safety Rules

- **Read-only on source data**: The agent must NEVER call any mutating GCP API (no deploy, no scale, no config change). Tools are limited to `entries.list`, `timeSeries.list`, `metricDescriptors.list`, and `topics.publish`.
- **Scoped to alert context**: The agent should only query the project and time window referenced in the alert (plus a small buffer, e.g., ±15 minutes). It must not freely explore unrelated projects.
- **No credentials in output**: Diagnosis reports must never include service account keys, tokens, or credential material.
- **Timeout protection**: Log/metric queries should use bounded time windows (max 1 hour) to prevent runaway API costs.

## Success Criteria

- Given a synthetic alert for a service with a clear fault (e.g., OOM, config error), the agent identifies the correct root cause category in ≥80% of eval cases.
- The diagnosis report includes at least one concrete log entry or metric data point as evidence.
- The agent handles alerts for ≥3 different service types (Cloud Run, GKE, Cloud Functions) without code changes.
- Output is valid JSON publishable to Pub/Sub with fields: `alert_id`, `project`, `service`, `severity`, `root_cause`, `evidence[]`, `suggested_actions[]`, `confidence`.

## Reference Samples

- `core/python/ambient-expense-agent` — Pub/Sub event-driven pattern, workflow-based processing, no chat loop. We adapt its message consumption and workflow structure for alert ingestion.

## Assumptions

- Auth via Application Default Credentials (ADC) or a dedicated service account with `roles/logging.viewer`, `roles/monitoring.viewer`, `roles/pubsub.publisher` on the target project(s).
- Input Pub/Sub topic and output Pub/Sub topic are configured via environment variables (`ALERT_INPUT_TOPIC`, `DIAGNOSIS_OUTPUT_TOPIC`).
- The agent runs in the same GCP project as the alerting service for v1 (multi-project via `GOOGLE_CLOUD_PROJECT` override or per-alert `project` field in the payload).
- Prototype-first: no deployment target yet; will be Cloud Run when we deploy.
